# 敵対的検証（設計時）

賛成側の案を一度捨てて、**壊し方・抜け・後戻りコスト**だけを探す。  
採用・却下の最終判断は **親エージェント＋人**。この skill は指摘と分類まで。

## いつ使うか（必須に近い）

- 実装前の計画・ロードマップ切片・スコープ切り
- `docs/product` / flows / acceptance の新規・大幅変更案
- Web / API / Mobile / DB の配置・境界・データ流のアーキ案
- Design Lab 前後の UI/UX 複数案比較
- 「これでよさそう」と合意しそうなとき（合意前に1回）

単色・文言のみ・既知バグの最小修正だけなら不要。

## やらないこと

| 禁止 | 代わり |
|------|--------|
| カスタム security サブエージェントの自作 | Cursor 組み込み `security-review` / `bugbot` |
| コード差分の脆弱性スキャンの代替 | 実装後は `secure-change-checklist` + 組み込みレビュー |
| 本番コードの自動改変 | 指摘のみ。修正は人が承認してから |
| 仕様・認可・採用の最終決定 | 親が持つ（`AGENTS.md` 委譲表） |
| ARCHIVE / Dash を正にした新設計 | `docs/product` / `docs/db` / `docs/design` / v2 rules |

## 手順

1. **対象を固定**（計画 / 仕様 / アーキ / デザイン案。混ぜたら層ごとに節を分ける）
2. **正本を開く**（該当するものだけ）
   - 製品: `docs/product/` + skill `product-spec-sync` の観点
   - 境界: `architecture.mdc` / `platform.mdc` / `auth.mdc` / `security.mdc`
   - DB: `docs/db/`（触る案なら `db-schema-change` 前提も）
   - UI: `docs/design/` + `design-lab` / `design-a11y`
3. 下の **観点チェック**を敵対的に通す（賛成コメントは書かない）
4. **出力テンプレ**で返す（重大度順）
5. 親へ: ブロッカーが残るなら実装着手を止め、要確認は質問リストにする

長い批判文だけ必要なときは **Task(`generalPurpose`)** に委譲可。委譲先は合否と要点のみ返す。判断は親。

## 観点チェック

### A. 製品仕様・価値

- [ ] 誰のどの痛みを、どの成功条件で解くか一文で言えるか（曖昧ならブロッカー）
- [ ] Must / Should / deferred が切れず、スコープが膨れていないか
- [ ] 既存 `docs/product`（roadmap / feature_status / acceptance）と矛盾していないか
- [ ] 空・途中離脱・権限なし・データ0件の受け入れが欠けていないか
- [ ] 「今やらなくてよいこと」が明示されているか

### B. アーキテクチャ・境界

- [ ] UI に業務本体を置いていないか（業務は `apps/api` `services/`）
- [ ] Web Cookie / API Bearer / Mobile SecureStore の前提を崩していないか
- [ ] 認証発行を Supabase Auth 以外に増やしていないか。API 検証は JWKS 前提か
- [ ] `members_id` = JWT `sub` + RLS を迂回する設計になっていないか
- [ ] `packages/shared` に秘密・環境依存ロジックを入れていないか
- [ ] 新規表・外部連携・バッチで service_role が「楽だから」増えていないか
- [ ] 命名・パスが glossary / `naming.mdc` / file_structure から外れていないか
- [ ] 単一障害点・後戻りコスト（スキーマ・公開 API）が過小評価されていないか

### C. 設計時セキュリティ（脅威モデル簡易）

コード差分レビューではない。**設計が攻撃面を増やしていないか**を見る。

- [ ] 信頼境界（ブラウザ / モバイル / API / DB / 外部 HTTP）が図または文章で分かるか
- [ ] 公開してよいもの（`NEXT_PUBLIC_*`・publishable）と secret の置き場が契約どおりか
- [ ] 認可は RLS + `members_id` が最終防衛か（`user_metadata` のみ認可は不可）
- [ ] IDOR・他人データ参照が「画面が隠すだけ」になっていないか
- [ ] アップロード・署名 URL・ログに秘密が乗る経路がないか
- [ ] 外部 API（IO/楽天等）のキー・レート・失敗時の漏洩がないか
- [ ] 新規公開エンドポイントの認証要否が明示されているか

実装後の差分確認は **組み込み `security-review`** と `secure-change-checklist` に渡す。ここでは設計上の穴だけ書く。

### D. デザイン・UX（案があるとき）

- [ ] 第1画面の仕事が1つか（ダッシュボード化・情報過多）
- [ ] 主CTA・エラー・空状態が各案で破綻していないか
- [ ] a11y（コントラスト・フォーカス・タップ・モーション）を後回しにして致命傷になっていないか
- [ ] Design Lab の軸（配置差 vs 色コピー）を守っているか。テーマ色欠落案は不合格
- [ ] Web とモバイルで前提（指・回線・SecureStore）が食い違っていないか

### E. 検証可能性・運用

- [ ] 受け入れをテストや手動チェックに落とせるか（落ちないなら仕様不足）
- [ ] 振る舞い変更なら TDD（`tdd-workflow`）前提が書かれているか
- [ ] デプロイ・env・CORS が増えるなら `deploy-change` / env-contract に触れるか
- [ ] 失敗時のユーザー向けメッセージとシステムログ方針が混同されていないか

## 出力テンプレ（必須）

```markdown
## 敵対的検証サマリ
- 対象: （計画 / 仕様 / アーキ / デザイン案）
- 結論: 進行可 | 条件付き | 差し戻し
- ブロッカー数 / 要確認数 / 許容数:

## 指摘（重大度順）
| 重大度 | 層 | 指摘 | 壊れるシナリオ | 推奨対応 |
|--------|----|------|----------------|----------|
| blocker / major / minor | 仕様/アーキ/設計時セキュ/UX/検証 | … | … | … |

## 今やらなくてよいこと
- …

## 親への確認質問（最大5）
1. …
```

重大度:

| ラベル | 意味 |
|--------|------|
| blocker | 実装着手前に解消必須 |
| major | 条件付き進行。未解消なら切り戻しコスト大 |
| minor | 記録して進めてよい |
