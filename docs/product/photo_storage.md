# 写真の保管画質と容量（無料／将来有料）

グッズ管理アプリとして、Storage には **表示・タグ・将来の類似検索に足りる解像度**だけを載せる。  
原寸マスターは必須にしない（印刷・入稿が必要なら手元／Drive 等の別置き）。  
アプリ内デコ（枠・シール等）も、無料ティア解像度で足りる想定。

関連実装: `apps/web/src/lib/prepareRegisterPhoto.ts`  
API 上限: `POST /photos` は **10MB**（`apps/api/app/routers/photos.py`）  
Supabase Free: 1ファイル最大 50MB・合計約 1GB（プラン制限。Dashboard の Global file size）

## いま（無料・既定）

| 項目 | 値 |
|------|-----|
| 長辺 | 最大 **2048px**（見た目の主因） |
| 目標サイズ | 約 **2.5MB** 以下（JPEG・容量の目安） |
| ハード上限 | **10MB**（API と一致） |
| タイミング | 登録ウィザードで写真選択直後＋本保存前の再確認 |
| 向き | EXIF を画素に焼く。足りないときは登録プレビューで左右回転 |

Vision・将来の CLIP 類似（入力はだいたい 224〜336px）にも十分な解像度。

## 有料化の方針（決定・2026-10-07）

### やってはいけない課金差

- **同じ長辺で「無料 2MB／有料 3MB」だけ**  
  - スマホの一覧・詳細では差がほぼ分からない  
  - 「払う理由」にならない  

ファイルサイズ（MB）は **副次**（通信・Storage コスト用）。ユーザー向け訴求の正面にしない。

### やる課金差（正）

1. **長辺（解像度）** — ピンチ・デコ・書き出しで差が出る  
   | プラン | 長辺の目安 | 目標 MB（副次） |
   |--------|------------|-----------------|
   | `free`（現行） | **2048** | ~2.5 |
   | `standard`（有料） | **3072** | ~6 |
   | `high`（有料） | **4096** | ~10（API 上限内） |
2. **合計容量（または枚数）** — 「もっと登録できる」が分かる  
   - アプリ側ソフトクォータ案: free ~200MB 相当／standard・high は数 GB 級（価格と Cloud 費用で再決定）  
   - 実装時は `member` または購読状態で判定し、超過時は分かりやすいエラー  

コード上の正: `PHOTO_QUALITY_TIERS` / `PHOTO_STORAGE_QUOTA_BYTES` / `resolvePhotoQualityTier`。

### 有料化時チェックリスト

- [ ] メンバーのプランを JWT または `member`／購読行で判別
- [ ] `resolvePhotoQualityTier(plan)` を登録・アップロード全経路で使う（無料を勝手に上げない）
- [ ] API 側でも長辺またはバイト上限をティア整合（クライアント改ざん対策）
- [ ] 設定 UI の説明は **「解像度」「保存できる量」** であり、「+1MB」ではない
- [ ] Supabase / ホスティング費用とセットで価格を決める

## やらないこと

- Free で Image Transformation に依存しない（Pro 機能）
- 学習用に原寸を外部へ残さない（登録フロー方針どおり）
- **MB 差だけのプレミアム**を商品にしない

## 既存写真の一括再圧縮（メンテ）

テスト／移行時のみ。`SUPABASE_SECRET_KEY` が必要（通常 CRUD 禁止の管理用）。

```powershell
$env:PYTHONPATH = "apps/api"
python scripts/recompress_existing_photos.py
```

同一 object path を upsert 上書きする。ギャラリーは **スーパーリロード** や再ログインで signed URL キャッシュを避けること。
